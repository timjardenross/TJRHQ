# Briefs — Canonical Morning Intelligence Uplift

**Status:** implemented (backend pipeline + frontend IA). See "What was
deferred" for the boundary of this pass.

**Product definition:** Briefs is HQ's canonical daily synthesis of the
intelligence picture, generated after the morning collection cycle and
preserved as the authoritative record of what HQ assessed at that point in
time. One intelligence assessment, multiple delivery formats.

---

## 1. Phase 0 audit — what was actually true before this uplift

Audited before any architecture change, per the mission brief. Findings,
with file:line evidence gathered during the audit:

### 1.1 Two brief stores, not one

- `intelligence_briefs` — the real ORI/OSINT brief. Generated by
  `intelligence/brief/brief_generator.py::BriefGenerator.generate()`.
  Auto-published at generation time (`intelligence/persistence/
  intelligence_store.py::save_brief()` hardcodes `approval_status:
  PUBLISHED`). Insert-only — no brief is ever updated, so history was
  already immutable. This is what `/briefs`, `/api/briefs`, and the
  Telegram `/brief` command read.
- `captains_daily_briefs` — written by `intelligence/captains_brief.py`
  and read by Captain's Chair's `TodaysBriefPanel.tsx` (via
  `/api/captains-daily-brief`). **Before this uplift**, its morning
  content came from `generate_morning_brief()` → `build_daily_digest()`,
  which took the canonical brief's `executive_snapshot`/`bottom_line` and
  fed it into a **second, independent LLM call** alongside platform
  `core_events` and individual signals — a fresh re-synthesis of "what
  matters today," not a rendering of the canonical brief. Telegram and
  Captain's Chair already agreed with *each other* (same table), but
  neither was a faithful rendering of `intelligence_briefs` — exactly the
  "second interpretation of the same morning" this mission targets.

### 1.2 Scheduling was real, not just UI copy — but pipeline-blind

`intelligence/config.py::SCHEDULE_CRON` defaulted to `"30 6 * * *"` (06:30
AEST), live APScheduler cron in `intelligence/scheduler.py`. The 06:30
default was genuine, but the trigger was a blind clock offset:
`_daily_collection_job` (06:00) and `BriefGenerator.generate()`'s own
independent `collect_all()` call (~06:30) had **no dependency
relationship** — every "after collection" reference in the scheduler was a
comment, not a check. No batch/run/cycle ID existed anywhere in the schema.
No degraded-source quorum/cutoff logic existed — `sources_checked/
available/failed/stale` were computed and stored but never gated
generation or appeared in the brief's narrative.

One genuinely reusable primitive already existed, though: `_daily_
collection_job` records a heartbeat to `domain_heartbeats` (migration
0071) for `domain_key='intelligence_collection'` as soon as its own
`collect_all()` finishes — the exact "explicit completion marker" Section
5 asked for, already wired for an unrelated purpose (Platform Health
deadman's switch). This uplift reuses it rather than inventing a new
mechanism.

### 1.3 Content model gaps

`intelligence_briefs` had no fields for what-changed, domain grouping, or
known-unknowns. It did have `top_events` (used to derive "what matters" —
each event already carries a `so_what` field), `forward_watch` (maps
directly to "watch"), and `executive_snapshot`/`bottom_line` (executive
read). No prior-brief comparison logic existed anywhere.

### 1.4 Detail routing

Only `/intelligence-workbench/brief/[id]` existed; no `/briefs/[id]`. That
page still carries a live (if vestigial) `IN_REVIEW → QA_PASSED →
PUBLISHED` action UI (QA Pass / Publish / Escalate to RED buttons posting
to `/api/intelligence-workbench/action`) even though every brief generated
since 2026-08-22 auto-publishes and never uses that state machine.

## 2. What was implemented

### 2.1 Event-driven generation with a bounded degraded cutoff (Sections 4-6)

New module `intelligence/brief/morning_cycle.py`. `intelligence/
scheduler.py`'s `or_intelligence_brief` job changed from a single fixed
`CronTrigger` to a 5-minute `IntervalTrigger` poll (`_brief_readiness_job`)
that:

1. No-ops outside a 05:00-09:00 local window (cheap, no network call).
2. Checks `domain_heartbeats` for today's `intelligence_collection`
   heartbeat (the existing 06:00 collection job's completion marker).
3. Generates as soon as it lands (`ready=True, degraded=False`), or once a
   bounded cutoff passes without it (`ready=True, degraded=True`) — derived
   from `OR_INTEL_SCHEDULE_CRON`'s configured time (default 06:30 AEST),
   overridable via `OR_INTEL_MORNING_CUTOFF="HH:MM"`.
4. Is idempotent: `intelligence_store.brief_exists_for_cycle()` skips
   regeneration once today's cycle already has a persisted brief.
5. Never hangs on a Supabase outage — an unreachable heartbeat check
   degrades at the cutoff instead of blocking indefinitely.

The normal completion time is still ~06:30 AEST when collection finishes
on time; the difference is the brief no longer fires blind to whether
collection actually finished.

### 2.2 Morning-cycle identifier (Section 5)

`morning_cycle_id` (new nullable column, `intelligence_briefs`) is the AEST
calendar date of the collection cycle (`'2026-09-06'`), not a new
UUID/table — avoids a schema migration across every ingestion table while
still letting the brief, the scheduler's idempotency check, and future
comparisons all agree on "which morning" a brief belongs to.

### 2.3 Coverage / degraded disclosure (Sections 6, 27, 28)

New `coverage` jsonb column, populated by `BriefGenerator.generate()` from
data it already computed (`sources_checked/available/failed/stale`) plus
the morning-cycle readiness check: expected/completed/failed counts,
missing source names, cutoff-reached flag, and the latest included item's
timestamp. Surfaced as a plain-language coverage note (`intelligence/
brief/render.py`) — "One intelligence source was unavailable during this
morning collection cycle" — never silently treated as "nothing happened."
Detailed per-source/job health stays in Agent & Job Status
(`domain_heartbeats`/`intelligence_source_health`); Briefs only shows what's
needed to interpret the brief, per Section 28.

### 2.4 Current-vs-prior comparison (Section 13)

New module `intelligence/brief/comparison.py`. Deterministic — no LLM call,
no invented history. Matches each of today's `top_events` against the
prior canonical brief's stored `top_events` by title similarity
(`difflib`) plus `event_type`, classifying NEW / ESCALATED / IMPROVED /
UNCHANGED_BUT_MATERIAL / NO_LONGER_MATERIAL from the two stored lists
only. Explicitly a bounded first version (only compares each day's top ~5
events, not full event history) — deeper day-over-day signal tracking is
FUTURE work.

### 2.5 Domain picture (Section 12)

New module `intelligence/brief/domain_picture.py`. Groups `top_events` by a
small fixed taxonomy derived from the `event_type` the classifier already
assigns (technical/regulatory/environmental/payments/other) — genuine
cross-domain structure over what the OSINT collector actually covers.
**Does not** claim Health OSINT or Emergency Alert Hub coverage — see §4.

### 2.6 Known unknowns (Section 11)

Added as one more key to the existing narrative LLM prompt in
`brief_generator.py::_generate_narrative()` — no new LLM call. Explicitly
instructed not to invent a gap if none exists (empty list is a valid,
expected result).

### 2.7 Telegram + Captain's Chair consolidation (Sections 9, 10, 26, 29)

New module `intelligence/brief/render.py` — `build_morning_intelligence_
view()` is the single canonical content selection (posture, top 3
what-matters with their existing `so_what`, what-changed, watch, coverage
note), built purely from fields already on the stored brief. No LLM call.

- `intelligence/captains_brief.py::generate_morning_brief()` now renders
  this view deterministically (`_format_intelligence_posture_block`) as
  its own section, instead of feeding the canonical brief's text into
  `build_daily_digest()`'s LLM call.
- `intelligence/brief/daily_digest.py` no longer accepts an `osint_brief`
  parameter — it's now scoped purely to the platform's own
  health/engineering/learning/opportunities/operational_intelligence
  `core_events` plus individual signals, which is legitimately separate,
  non-intelligence content this mission doesn't govern.
- Captain's Chair (`captains_daily_briefs` → `TodaysBriefPanel.tsx`)
  inherits the fix automatically: it reads the same table
  `generate_morning_brief()` persists to, so once that function stopped
  re-synthesizing, Captain's Chair stopped seeing a re-synthesis too.
- `telegram-bots/xo/app.py::cmd_brief` now renders the same
  `build_morning_intelligence_view()` selection (What Matters / Changed
  Since Yesterday / coverage note) in addition to its existing
  canonical-store fields, and no longer blindly kicks off a ~15-25min
  regenerate when today's cycle already has a brief or collection is still
  in progress — it says which honestly (Section 25).

Section 29's testable guarantee — no channel invents a posture or
development the canonical brief doesn't state — is covered by
`tests/test_brief_canonical_uplift.py` (`TestRenderConsistency`,
`TestCaptainsBriefIntelligencePosture`): Telegram's view and Captain's
Chair's excerpt are asserted to come from the exact same function call.

### 2.8 Briefs web IA (Sections 14-21, 24)

- `/briefs` rebuilt around **Latest / Timeline / Explore** instead of
  publication-state tabs.
  - **Latest**: today's (or most recent) canonical brief rendered as a
    product — posture, executive read, what matters, what changed, watch,
    coverage — not a single archive row. Honest empty/in-progress/degraded
    states (Section 24) instead of "No intelligence."
  - **Timeline**: chronological historical record, newest first.
  - **Explore**: search/filter/archive, with the legacy `IN_REVIEW`/
    `QA_PASSED` states demoted to an advanced filter (Section 18) rather
    than primary tabs.
- New canonical `/briefs/[id]` detail route + `/api/briefs/[id]` endpoint,
  reusing the same query shape as the existing workbench detail API.
- `/api/briefs` extended to select the new columns needed by Latest/
  Timeline (`top_events`, `coverage`, `comparison`, `domain_picture`,
  `known_unknowns`, `morning_cycle_id`) in addition to its existing 7.

## 3. Deliberate non-changes (and why)

- **`/intelligence-workbench/brief/[id]` is not redirected** to
  `/briefs/[id]`. That page still carries the live QA Pass / Publish /
  Escalate action buttons (`/api/intelligence-workbench/action`) for
  pre-2026-08-22 legacy-workflow briefs. A redirect would silently remove
  access to those actions for anyone still using them from a workbench
  cross-link, which the mission explicitly asks to avoid ("do not break
  old bookmarks or cross-workbench links"). `/briefs` now links to the new
  canonical `/briefs/[id]` directly, so the legacy route is no longer the
  primary path, but it keeps working. Whether to retire those action
  buttons entirely (they're vestigial for anything auto-published) is a
  product decision for a follow-up, not made here.
- **No new "Generate now" button in the web UI.** No canonical on-demand
  generation service is exposed to the browser today (only Telegram's
  `/brief` triggers `intelligence.scheduler --once` via a detached
  subprocess) — adding a web button would mean either duplicating that
  trigger path or exposing a new one, both out of scope per Section 24's
  "do not invent a new duplicate generation path merely to add a button."

## 4. What was deferred as FUTURE (not implemented)

- **Health OSINT and Emergency Alert Hub are not fused into the ORI
  brief's evidence base.** They run on entirely separate schedules
  (Health OSINT: weekly, Sunday 02:00; Emergency Alert Hub: continuous,
  every 15 min) and write to separate tables never read by
  `BriefGenerator.generate()`'s `collect_all()`/classify/rank pipeline.
  `domain_picture` therefore only ever produces buckets the OSINT
  collector actually covers (technical/regulatory/environmental/
  payments) — it does not claim Health or Emergency coverage. A concrete,
  decoupled design for closing this gap is specified in §4.1 below — not
  yet built, pending sign-off, since it changes the live generation
  pipeline this PR ships.

### 4.1 Decoupled integration design: Health OSINT + Emergency Alert Hub → Briefs

Audited as a follow-on to this PR (2026-09-06). The goal: let these two
pipelines' already-*assessed* output reach the brief's one synthesis step,
without Briefs importing either pipeline's ingestion/collector code — the
same data-boundary-not-code-boundary pattern this codebase already uses for
`domain_heartbeats`/`domain_heartbeat_latest` (migration 0071, read by
`infra_narrative.py`, `verification_engine.py`, a Next.js API route — none
of which import the heartbeat-writing code) and
`intelligence_source_health_latest` (migration 0190, read by two workbench
API routes, not by the collector that writes it).

**Health OSINT.** Assessed output lives in `health_signals`, gated by
`suppressed = false` (curation sets this plus `auto_ingest_reviewed = true`
on publish — see `tools/health-osint/health_signal_curation.py`). No new
view is needed: `suppressed=false` is already a stable predicate, not a
rolling log needing a `DISTINCT ON` collapse. This exact read already
exists cross-module — `intelligence/captains_brief.py::
_get_weekly_health_signals` reads `health_signals?suppressed=eq.false&...`
via the same plain PostgREST `_get()` idiom as `intelligence_store.py`,
with zero import of `health_signal_curation.py` or
`health_signal_ingestion.py` (which would otherwise pull in LLM provider
clients, Firecrawl/BrightData scraper clients, and ingestion
budget-circuit-breaker state into Briefs' import graph).

**Emergency Alert Hub.** Assessed output lives in `alerts`, gated by
`is_active = true` — a first-class lifecycle column (migration 0174), not a
raw feed log. `emergency_alert_summary.py`'s own hourly digest already
reads exactly this shape (`alerts?is_active=eq.true&order=...&select=...`).
No consumer outside that module reads it yet, but the contract to copy
already exists in-repo. Importing `emergency_alerts.py` directly would pull
in all 9 government-feed scraper adapters plus an email-sending client;
importing `emergency_alert_summary.py` would pull in another LLM client —
both avoided by a plain `_get()` read.

**Recommended shape, not yet implemented:**
1. `intelligence_store.py`: `load_assessed_health_signals(since)` and
   `load_active_emergency_alerts()` — two new thin readers, same `_get()`
   idiom as every existing reader in that file.
2. A small `ExternalDomainSignal` record (title, domain tag `"health"` /
   `"emergency"`, severity, source_id, assessed_at) — deliberately not
   forced through `ClassifiedEvent`/`RankedEvent` (wrong shape for
   non-OSINT content, same reasoning `daily_digest.py` already applies to
   platform `core_events`).
3. `domain_picture.py` gains `health`/`emergency` buckets fed from these
   signals directly alongside the existing OSINT-derived buckets — genuine
   cross-domain grouping, still fully deterministic.
4. `coverage` gains these two sources in its `expected`/`completed`/
   `failed` counts, so a Health OSINT or Emergency Alert Hub outage is
   disclosed exactly like an OSINT source outage is today.
5. `_generate_narrative`'s prompt gets these signals appended to
   `event_summaries` under the same "only use information provided, do not
   invent" instruction it already carries — this is what makes the
   existing single synthesis step genuinely cross-domain, without adding a
   second LLM call anywhere in the pipeline.

This does not touch Telegram, Captain's Chair, or `render.py` — they stay
purely selection-based against whatever `intelligence_briefs` ends up
storing, per §4.2.

### 4.2 Confirmed: the one canonical synthesis step was not removed

Re-verified directly against the shipped code, not just Phase 0's audit:
`brief_generator.py::_generate_narrative` is untouched by this PR except
for adding `known_unknowns` to its JSON schema — it is still the single LLM
call responsible for interpreting *why* the top events matter
(`executive_snapshot`/`bottom_line`), and it still runs before any
downstream rendering. `render.py` (confirmed via inspection: zero LLM
calls) and `captains_brief.py::_format_intelligence_posture_block` only
select fields this one step already produced. `daily_digest.py`'s
remaining LLM call is scoped to genuinely separate platform `core_events`
content (health/engineering/learning/opportunities logs) that was never
part of `intelligence_briefs` — it does not re-reason the brief's own
assessed content.

The real limitation is scope, not removal: this one synthesis step has
*always* only seen OSINT/world-news events (true before this PR too) — it
was never fed Health OSINT or Emergency Alert Hub content. §4.1's design
is what would make it genuinely cross-domain.
- **"Not Material Today" section** — not implemented. No reliable,
  non-noisy way to populate it from current data without either dumping
  every suppressed event (noise) or inventing a judgment the generator
  doesn't actually make. Left out per Section 11's "do not fabricate
  sections the generator cannot actually support."
- **Deeper day-over-day comparison** (beyond each day's top ~5 events) —
  the bounded first version in `comparison.py` is intentionally limited;
  a real signal-level history table is future work (Section 13).
- **Compare UI** (Section 21, Phase 10) between two arbitrary historical
  briefs — the underlying `comparison` field only exists for pairs of
  *consecutive* canonical briefs (computed at generation time against the
  immediately prior brief), not for arbitrary pairs. An on-demand
  arbitrary-pair compare view is future work once that field is proven
  reliable in daily use.
- **Self-Improvement evidence surface** — this uplift preserves the
  metadata (`coverage`, `comparison`, `morning_cycle_id`) a future
  Self-Improvement pass would need (did HQ identify a risk early, was
  coverage degraded before a miss, did posture escalate), but does not
  build any evaluation surface itself, per the mission's explicit
  boundary.
