# Chief Engineer Architecture Review — XO Telegram Bot

USS TJR — Registry USS-TJR-003, Engineering Division, Advisory authority
Reviewer: Chief Engineer persona
Date: 2026-08-09
Scope: `/opt/starship-endeavour/telegram-bots/xo/` (app.py, voice_capture.py, pulse_time.py, test_voice_capture.py), `tg-xo.service`, live host state (systemctl/journalctl), and adjacent doc/env/API surface this bot depends on.

## Mission Summary

Real, grounded architecture and security review of the XO Telegram bot — the only Telegram bot still active on the platform (confirmed live: `tg-xo.service` active/running since 2026-07-31, PID 3637770; `starfleet-slack-bot.service` confirmed `inactive`/`disabled`). Is this code safe, correct, and well-architected as actually deployed.

## Assessment

### 1. Auth/allowlist enforcement — CRITICAL GAP, confirmed live

`core/platform/telegram_access.py` (`is_allowed()`) is the canonical chat-ID allowlist gate. Its own docstring says it "retires the inline single-ID equality checks that were duplicated across telegram-bots/xo/app.py's 6 command handlers." That was true at the time it was written. It is no longer true.

I enumerated every handler registered in `main()` (`app.py:2279-2317`, 36 registrations) against every call site of `_chat_is_allowed()` (`app.py:96`, imported from that module). Only **10 of 36 handlers** call it:

- Gated: `cmd_restart_bots` (555), `cmd_learning` (880), `cmd_patterns` (935), `cmd_captain` (1590), `cmd_pending` (1621), `cmd_voice_note` (1841), `cmd_debrief_close` (1985), `cmd_debrief_weekly` (2009), `handle_voice_capture_callback` (2021), `handle_voice_debrief_decision_callback` (2087).
- **Not gated** (26 handlers, no chat-ID check anywhere in the call path): `cmd_start`, `cmd_help`, `cmd_recovery_status`, `cmd_recovery_pulse`, `cmd_db_status`, `cmd_log_activity`, `cmd_log_weight`, `cmd_dispatch`, `cmd_brief`, `cmd_daily`, `cmd_mission_list`, `cmd_mission_status`, `cmd_mission_create`, `cmd_captain_approve`, `cmd_captain_reject`, `cmd_mission_submit`, `cmd_handoff_engineering`, `cmd_operating_picture`, `cmd_signals`, `cmd_themes`, `cmd_source_status`, `cmd_advise`, `cmd_challenge`, `cmd_note`, `handle_outcome_callback`, `handle_pulse_callback`, and the free-text catch-all `cmd_message` (the LLM conversation path, `app.py:1701-1741`).

There is no global gate either — `main()` (`app.py:2273-2320`) registers every `CommandHandler`/`CallbackQueryHandler`/`MessageHandler` with no `filters.Chat(...)` and no group `-1` pre-handler. Each handler is individually responsible for calling the shared gate, and most simply don't.

This is not theoretical. The bot's Telegram username is public (`@Starship_endeavour_xO_bot`, referenced in `app.py:1` and `/start`'s own reply text). Telegram privacy mode does not restrict who can open a 1:1 DM with a public bot. Any Telegram user who messages this bot can, today, without any credential:
- Create missions (`cmd_mission_create`, writes via LCARS API)
- **Approve or reject missions** — `cmd_captain_approve`/`cmd_captain_reject` (`app.py:1094-1126`), i.e. bypass Captain governance entirely
- Submit missions for approval and hand off to Engineering (`cmd_mission_submit`, `cmd_handoff_engineering`)
- Log fabricated weight/activity data as the Captain (`cmd_log_weight`, `cmd_log_activity`)
- Log fabricated recovery pulses via the inline button flow (`handle_pulse_callback`, `app.py:1746` — not gated at all, and it's the primary write path for `recovery_pulses`, the same table the recovery-confidence engine reads to decide whether to gate mission work)
- Read mission lists/status, intelligence briefs, signals, source health, the full Operating Picture, and learning/pattern data
- Converse with the backing LLM as if they were the Captain (`cmd_message`), burning Ollama Cloud spend and receiving the Captain's live recovery/wellness/mission context back in the system prompt (`_xo_system_prompt`, `app.py:192-235` — this leaks Captain health signals, open mission titles, and recovery confidence to whoever is messaging the bot)

I checked whether the `X-Bot-Secret` header (`_bot_headers()`, `app.py:133-136`) that XO sends on every LCARS Portal API call closes this gap. It does not: `lcars-portal/src/middleware.ts:50-58` accepts any request to `/api/*` bearing a valid `x-bot-secret` matching `BOT_API_SECRET`, with **no per-caller distinction** — it authenticates "this is XO the bot," not "this is the Captain talking to XO." XO always attaches this header regardless of who is driving it. So the per-command `_chat_is_allowed()` check inside `app.py` is the *only* control standing between an anonymous Telegram user and mission governance actions, and it is absent from every governance-mutating handler (`cmd_captain_approve`, `cmd_captain_reject`, `cmd_mission_submit`, `cmd_handoff_engineering`, `cmd_mission_create`).

**Severity: Critical.** This is a live, remotely-triggerable authorization bypass on Captain-governance actions, not a hypothetical.

### 2. Secret handling — CRITICAL, live exposure channel confirmed

- `TELEGRAM_BOT_TOKEN` is loaded from `telegram-bots/xo/.env` (`app.py:34,61`), file permissions correctly `600 root:root` — good.
- However, `logging.basicConfig(level=logging.INFO, ...)` (`app.py:71-75`) sets the **root logger** to INFO with no suppression of third-party loggers. `python-telegram-bot`'s underlying `httpx` client logs the full request URL at INFO level for every `getUpdates`/`sendMessage` call, and that URL embeds the bot token (`https://api.telegram.org/bot<TOKEN>/getUpdates`). I confirmed this live: `journalctl -u tg-xo.service -n 500` shows **497 of the last 500 log lines** contain the live, working bot token in plaintext. This has been happening continuously since the service started (2026-07-31) and will keep happening on every poll cycle (~every 10s).
- Impact: anyone with read access to the systemd journal for this unit (root, sudo group, `adm`/`systemd-journal` group members, anything that ships these logs off-box — e.g. a log aggregator, backup, or another compromised service on the host) can extract a live-usable bot token, without ever touching the `.env` file. A stolen token lets an attacker call `sendMessage` as XO, or race the legitimate poller for `getUpdates` (Telegram allows only one long-poll client per token — a second poller can starve or disrupt the real bot).
- `SUPABASE_KEY` (`app.py:64`) is a **`service_role`** JWT — I decoded the JWT `role` claim locally (did not print the key) and confirmed `role: service_role`. This bypasses Postgres RLS entirely for every table the bot's Supabase client touches (`missions`, `recovery_pulses`, `activity_logs`, `weight_logs`, `captured_items`, `intelligence_briefs`, `intelligence_events`, `intelligence_source_health`/`_registry`). Combined with Finding 1 (most handlers ungated), an unauthorized caller reaches full-service-role-privilege reads/writes across all of those tables with zero RLS backstop — the bot-level chat-ID check was the *entire* access-control layer, and it's mostly missing.
- `.env.example` (`telegram-bots/xo/.env.example:9`) documents `SUPABASE_KEY=<supabase-anon-or-service-role-key>` as if the two are interchangeable. They are not — an anon key would at least leave RLS as a backstop for the auth gap above; a service-role key removes that backstop entirely. This is a security-relevant naming/documentation choice, not just cosmetic.
- `_ensure_mistral_env()` (`app.py:37-56`) reads `platform-runtime/.env` and copies `MISTRAL_API_KEY` into this process's environment (with `os.environ.setdefault`, existing value always wins — correctly scoped to one specific key, not a blanket import). That key is then inherited by any subprocess this process spawns (e.g. `core/advisory/cli.py` via `_advisory_cli_call`, `app.py:1513-1523`). This is intentional and documented in the function's own docstring, and is scoped narrowly enough not to be a material risk — noted for completeness, not flagged as a defect.
- `TELEGRAM_ALLOWED_CHAT_IDS` is **not set** in either `telegram-bots/xo/.env` or `platform-runtime/.env` (confirmed via grep). `telegram_access.allowed_chat_ids()` therefore always falls back to the single `bootstrap_captain_chat_id` (`TELEGRAM_CHAT_ID`). That module's own docstring flags this exact situation as a state that should not persist indefinitely. It has persisted since the module was built (SUOC Wave 2 / MSN-0210F Item C). Low risk on its own (the fallback ID is correct) but it means the "long-term authority model" the module was designed around was never actually adopted for this bot.

### 3. `restart_bots` / subprocess calls — no injection risk, one stale-target note

`cmd_restart_bots` (`app.py:553-589`) resolves the user's `arg` through a dict lookup (`_RESTARTABLE_SERVICES.get(arg, _RESTARTABLE_SERVICES["all"])`, `app.py:559`) — the actual `subprocess.run(["systemctl", "restart", svc], ...)` argument (`app.py:570-573`) always comes from the hardcoded whitelist, never from raw user text, and `subprocess.run` is called with a list (no `shell=True`), so there's no shell-injection surface here. This one is well built.

`_RESTARTABLE_SERVICES` (`app.py:546-550`) currently maps `"slack"` and `"all"` to `["starfleet-slack-bot.service"]`, and `"telegram"` to `[]` (XO restarts itself separately via the hardcoded `subprocess.Popen(["systemctl", "restart", "tg-xo.service"])`, `app.py:589`). I confirmed live: `starfleet-slack-bot.service` is `inactive`/`disabled`. Restarting a disabled unit is harmless (systemd will restart it and it'll just run once unless re-enabled), so this isn't a bug, but the list's only non-self target currently points at a bot that's intentionally retired — worth a comment update so a future reader doesn't assume it's live. This command is one of the ten that *is* correctly chat-ID gated (`app.py:555`), so the injection-adjacent risk (arbitrary `systemctl restart` on other units) is at least behind the same allowlist gap described in Finding 1 — meaning it inherits that gap too.

### 4. Error handling — mostly good, one compounding issue

- `_on_error` (`app.py:2264-2270`) is a real global backstop registered via `app.add_error_handler` — logs the exception, does not attempt to reply, does not leak to chat. This is a legitimate fix for a previously-real gap (the comment explains a prior silent-failure mode).
- `cmd_message` (`app.py:1701-1741`) wraps its whole body in try/except and replies with a generic message on failure — good, doesn't leak internals, and the comment explains this was retrofitted after a real silent-crash bug.
- Most other handlers catch narrowly and reply with `str(exc)[:80..120]` truncated into the chat (e.g. `cmd_mission_list` at `app.py:774-779`, `cmd_signals` at `1367-1372`, `cmd_captain_reject`/`_captain_decision_via_api` at `1086-1091`). This is a minor information-disclosure pattern on its own (surfaces raw Supabase/httpx exception text, which can include table/column names) — normally low severity since only the Captain should see it, but it compounds Finding 1: since most of these handlers aren't chat-gated, that exception detail is exposed to anyone who can message the bot, not just the Captain.
- `_write_pulse` (`app.py:289-325`) and Supabase-down paths generally **fail closed with a visible warning** (`"Supabase unavailable (check SUPABASE_KEY)"`), not silently — correct behavior, no fail-open pattern found on the DB-availability axis.

### 5. Deploy/README doc drift — confirmed, two separate instances

**a) `deploy/README-xo-bot.md` — describes a different bot entirely, confirmed stale.** It documents a "planner.py → executor.py, per-step Approve/Skip/Cancel, full host/shell control" architecture, a `xo-bot/` directory, env vars `XO_BOT_TOKEN`/`XO_ALLOWED_CHAT_IDS`, an `/audit` command and JSONL audit log, and installs `deploy/xo-bot.service`. None of this exists in the live deployment: the `xo-bot/` directory does not exist on disk (`ls` confirms), there is no `planner.py`/`executor.py`/`actions.py`/`shellrun.py` anywhere in `telegram-bots/xo/`, no `/audit` or `/cancel` command is registered in `main()`, and the live unit is `tg-xo.service`, not `xo-bot.service`. `deploy/xo-bot.service` itself carries a header comment explaining why: that architecture was superseded 2026-07-05 and moved to `xo-bot.DEPRECATED-2026-07-05/`, and the service file was corrected 2026-07-12 to point at the real unit — but **the README's body content was never updated to match**, so it still reads as current documentation for the deleted design. This is the exact drift pattern flagged in the review brief, and it's still live.

**b) `telegram-bots/xo/DEPLOYMENT.md` — partially stale, on the live bot itself.**
- It instructs operators to verify the scheduler via `grep "AsyncIOScheduler" telegram-bots/xo/app.py` and asserts "the bot uses AsyncIOScheduler ... NOT BackgroundScheduler" (`DEPLOYMENT.md:33-44`). I grepped `app.py`, `voice_capture.py`, and `pulse_time.py` for `apscheduler`/`AsyncIOScheduler`/`BackgroundScheduler`/`scheduler` — zero matches anywhere except a string literal telling users to run `intelligence.scheduler --once` (`app.py:621`). The bot does not self-schedule anything; proactive pushes (07:00 morning brief etc., as advertised in `/help`, `app.py:382-387`) are owned by the separate `intelligence-scheduler.service`, which I confirmed live and actively delivering (`journalctl -u intelligence-scheduler.service` shows successful morning-brief deliveries on 2026-08-07/08/09 at 07:00). `apscheduler==3.10.4` is still listed in `requirements.txt` — a dead dependency, a vestige of whatever pre-refactor version of this bot DEPLOYMENT.md still describes.
- Its example systemd unit (`DEPLOYMENT.md:46-62`) shows a single `EnvironmentFile=/opt/starship-endeavour/telegram-bots/xo/.env`. The live `tg-xo.service` (and the current `deploy/xo-bot.service`) load **two** env files — `platform-runtime/.env` first, then `xo/.env` — and `deploy/xo-bot.service`'s own header comment explains this was a real production bug: without the `platform-runtime/.env` line, `EMBEDDING_PROVIDER` was unset and fell back to a 1024-dim default against a 768-dim schema, silently degrading `/advise` and `/challenge`. Following `DEPLOYMENT.md`'s documented unit as written would reintroduce that already-fixed bug.
- The `.env` block and Post-Deploy Verification section are accurate and still useful.

Net: the operationally load-bearing deploy artifact (`deploy/xo-bot.service`) is correct and self-documents its own history well; the two markdown docs someone would actually read first (`deploy/README-xo-bot.md` fully, `telegram-bots/xo/DEPLOYMENT.md` partially) would send an operator down a wrong or previously-broken path.

### 6. A third drift I wasn't asked to look for but found: `debrief_engine.py` does not exist in the live deployment

`app.py` imports `telegram_bots.xo.debrief_engine` in five places (`cmd_message` at 1715, `cmd_voice_note` at 1864, `cmd_debrief_close` at 1993, `handle_voice_debrief_decision_callback` at 2128) and calls it in a sixth path implicitly through `cmd_debrief_weekly`'s comment structure. I confirmed via direct Python import inside the bot's own venv that `telegram_bots.xo.debrief_engine` **fails to import** — the file is not present anywhere in the live repo. A stale compiled artifact (`debrief_engine.cpython-312.pyc`) exists only inside a dated backup tree (`/opt/starship-endeavour.USSTJROS-backup-20260719/telegram-bots/xo/__pycache__/`), meaning the module existed as of ~2026-07-19 and is now gone from the live checkout. `git log --all` returns **zero commits** for this filename in any branch — it was apparently never committed, so there's no way to recover it from version control; whatever last had it was a local, uncommitted state on a different host or a previous deploy.

Consequences:
- Every voice note the Captain sends degrades to plain quick-capture (the `de is None` fallback path, `app.py:1918,1933`) instead of ever offering a real debrief session — silently, with no error surfaced (the `except ImportError: de = None` branches in `cmd_message`/`cmd_voice_note` don't even log a warning).
- `/debrief_close` and the "Start Debrief" button (`handle_voice_debrief_decision_callback`'s `debrief` action) both correctly catch this and tell the Captain "the module isn't present on this deploy" — the one place this is handled with a clear, honest user-facing message rather than silent degradation.
- Given `app.py` was last modified 2026-08-07 (per file mtime) and clearly still assumes this module exists in five separate call sites, this reads as debrief functionality being actively developed/half-shipped, with the actual engine file lost between environments rather than removed on purpose.

### 7. Test coverage

`test_voice_capture.py` — 173/173 tests pass (ran directly; `unittest` module discovery finds 0 because the tests are plain asserts run via `if __name__ == "__main__"`, not `unittest.TestCase` classes — discoverable only by executing the file directly, not by `python -m unittest discover` or `pytest` without a plugin). Coverage is real and good *for what it covers*: `classify_text`, `transcribe_audio` error paths, `save_capture`, and especially `promote_recovery_pulse`'s merge/idempotency/no-fabrication guarantees are thoroughly exercised.

That file covers **only `voice_capture.py`** (363 lines). `app.py` (2324 lines, ~88% of this bot's code, and where every finding above lives) has **zero test coverage** — no test exercises `_chat_is_allowed` gating, command routing, the `restart_bots` subprocess path, the mission-governance API calls, or the free-text LLM path. Given Finding 1 is an authorization bug, the absence of any test that would have caught "handler X doesn't call the auth gate" is itself notable — a single parametrized test iterating over all registered handlers and asserting each mutating one calls the gate would have caught this class of regression before it reached production.

## Recommendations

Ordered by priority; 1–3 are security-critical and should not wait for a full sprint.

1. **(Escalate — Security, Critical) Close the auth gap.** Apply `_chat_is_allowed()` (or Telegram's own `filters.Chat(chat_id=...)` at registration time, which would be simpler and impossible to forget per-handler) to every mutating and data-exposing handler, starting with the five governance/write paths: `cmd_captain_approve`, `cmd_captain_reject`, `cmd_mission_submit`, `cmd_handoff_engineering`, `cmd_mission_create`, plus `handle_pulse_callback` and `cmd_log_weight`/`cmd_log_activity`. This is the single highest-impact fix in this review — it is a live authorization bypass on Captain governance actions, remotely triggerable by anyone who finds the bot's public username. This is a security risk per the persona's escalation rule and needs Captain visibility, not a quiet PR.
2. **(Escalate — Security, Critical) Stop logging the bot token.** Silence or filter the `httpx`/`telegram` loggers below INFO (or scrub the URL) so the token stops landing in `journalctl` on every poll cycle. Then rotate `TELEGRAM_BOT_TOKEN` via @BotFather, since the current one has been exposed in plaintext in the journal continuously since 2026-07-31 and should be treated as already compromised.
3. **(Security) Reconsider the `service_role` Supabase key.** Either move to RLS-scoped access with a narrower key/policy set, or — if `service_role` is genuinely required for what this bot does — treat Finding 1's fix as non-optional, since right now the bot-level chat check is the *only* thing standing between an anonymous caller and full-service-role DB access. Also fix `.env.example`'s "anon or service-role key" framing — it should state the security implication of choosing one over the other, not present them as interchangeable.
4. **(Doc hygiene) Retire or rewrite `deploy/README-xo-bot.md`.** It describes an architecture that was deleted 2026-07-05. Either delete it (the file's own sibling, `deploy/xo-bot.service`, already explains the supersession in its header) or replace its body with an accurate description of the current command-handler bot, matching the pattern `deploy/xo-bot.service` already sets.
5. **(Doc hygiene) Fix `telegram-bots/xo/DEPLOYMENT.md`'s scheduler section and systemd snippet.** Remove the AsyncIOScheduler claim (or replace it with an accurate note that proactive scheduling lives in `intelligence-scheduler.service`, not in this process), update the systemd example to the real two-`EnvironmentFile` unit, and drop `apscheduler` from `requirements.txt` since nothing imports it.
6. **(Correctness) Resolve the missing `debrief_engine.py`.** Either restore/recommit the module (check the 2026-07-19 backup host or whoever's local checkout still has it) or, if debrief-via-voice isn't ready to ship, remove the five call sites in `app.py` that assume it exists and ship the quick-capture-only path cleanly instead of silently degrading. At minimum, add a `log.warning` to the two `except ImportError: de = None` branches that currently swallow this without a trace — right now the only visible signal that debrief is broken is the Captain never getting the feature they might be expecting.
7. **(Test coverage) Add handler-level tests for `app.py`**, prioritizing exactly the gap that let Finding 1 happen: a test that walks every registered handler and asserts every one that writes to the DB or calls the LCARS governance API is gated by `_chat_is_allowed`. This is cheap to write and would prevent the next handler added without the check.

## Next Actions

1. Fix and deploy the auth-gate closure (Recommendation 1) — this is the next concrete step and should happen before anything else on this list, given it's a live, externally-reachable gap on governance actions.
2. In the same change or immediately after, silence the token-in-logs issue and rotate the token (Recommendations 2), since the current token must be assumed already exposed to anyone who's had journal access at any point since 2026-07-31.
3. Bring this to the Captain explicitly — both Critical items are security findings on a system with governance-approval and health-data write access, which is this persona's mandatory escalation trigger, not a judgment call to fix quietly and report after the fact.
