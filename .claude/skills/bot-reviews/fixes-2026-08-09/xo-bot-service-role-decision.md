# XO Telegram Bot — `service_role` Supabase Key: Architecture Decision

USS TJR — Registry USS-TJR-003, Engineering Division, Advisory authority
Reviewer: Chief Engineer persona
Date: 2026-08-09
Source finding: `.claude/skills/bot-reviews/xo-telegram-bot/chief-engineer-review.md`, Finding 2 / Recommendation 3 — "the bot uses a `service_role` Supabase key with no RLS backstop," raised in the context of tonight's RLS tightening on `intelligence_events`, `intelligence_briefs`, `intelligence_source_registry`, `audit_events`, `comms_content_revisions`.

## Decision (short version)

**Keep `service_role`. Document it as an accepted, understood architecture choice (Option A), not a gap.** The already-shipped global auth gate (`_global_auth_gate`, `app.py:2280-2297`, commit `fc24c93`) is the real compensating control, and it is the *only* control that can be, because RLS structurally cannot see which Telegram chat triggered a request. A narrower, genuinely-better alternative (Option C below — a scoped Postgres role reusing this platform's own proven pattern) exists and is worth doing, but it's a real production-risk architecture change and is specced here for Captain sign-off, not implemented speculatively.

## 1. Facts established (verified live, this session)

- **`SUPABASE_KEY` in `telegram-bots/xo/.env` is the `service_role` key** — confirmed by decoding its JWT payload directly: `role: service_role`. It is byte-identical to `SUPABASE_SERVICE_ROLE_KEY` in the same file. `app.py:64` reads it into `SUPABASE_KEY`; `_get_supabase()` (`app.py:120-132`) constructs the official `supabase-py` client with it. `pg_roles` confirms `service_role` has `rolbypassrls = true` — it bypasses RLS on every table in the database, not just the ones the bot touches.
- **The database has 112 tables in `public`.** XO's own code (`app.py`, `voice_capture.py`, `pulse_time.py`) issues `.table(...)` calls against exactly **9**: `missions` (read-only — 3 `select` call sites, no write), `recovery_pulses` (`select` + `upsert`), `recovery_confidence_today` (a view, `select` only, RLS disabled on the view itself), `activity_logs` (`insert`), `weight_logs` (`upsert`), `intelligence_briefs` (`select`), `intelligence_events` (`select`), `intelligence_source_health` (`select`), `intelligence_source_registry` (`select`), and `captured_items` (`select`/`insert`/`update`/`delete`). Governance-mutating actions — `/mission_create`, `/captain_approve`, `/captain_reject`, `/mission_submit`, `/handoff_engineering` — do **not** touch Supabase directly at all; they call the LCARS Portal HTTP API (`httpx` requests to `LCARS_PORTAL_URL/api/missions/...` with the `X-Bot-Secret` header, `app.py:991-1156`). So the `service_role` key's actual footprint in this bot's own code is ~10 tables, not 112 — but because `service_role` bypasses RLS unconditionally, the *key itself* is not scoped to that footprint; a bug or future change touching any of the other 102 tables would have identical unchecked access.
- **The RLS policies on every table XO touches are coarse, not per-user.** Queried `pg_policies` for all 9 tables live:
  - `missions`, `activity_logs`, `weight_logs`, `intelligence_briefs`, `intelligence_events`, `intelligence_source_registry`, `captured_items` (select/insert/update) all grant **blanket `USING (true)` / `WITH CHECK (true)` to the `authenticated` role** — no `auth.uid()` check, no per-user or per-tenant scoping anywhere in any of these policies. Any authenticated Supabase session — not just "the Captain's" — already has full CRUD on these tables today.
  - `intelligence_source_health` grants `SELECT` to `public` (anon-readable).
  - `recovery_pulses` has a **dedicated `service_role`-only INSERT policy**, kept *alongside* the `authenticated` one. I found the migration that documents why (`core/infrastructure/supabase/migrations/0110_tighten_recovery_pulses_and_activity_logs_rls.sql`, part of tonight's own RLS-tightening pass): its comment states verbatim that `recovery_pulses` "is also written by the Telegram-bot backend, not just the UI" and deliberately preserves the `service_role` INSERT policy for that reason. **Whoever wrote tonight's RLS migrations already made this exact call for this exact table, consciously, tonight.**
  - `captured_items` has **no DELETE policy for `authenticated` at all** (only insert/select/update). `app.py:2148` does `db.table("captured_items").delete()...` on a live path (clearing a captured item when the Captain starts a voice debrief session, `handle_voice_debrief_decision_callback`). This is load-bearing evidence for §3 below.
- **The global auth gate is real and already shipped.** `_global_auth_gate` (`app.py:2280-2297`) is registered via `app.add_handler(TypeHandler(Update, _global_auth_gate), group=-1)` — PTB's group `-1` runs before every other handler group, and the gate raises `ApplicationHandlerStop` (silent drop, no reply) for any chat that fails `_chat_is_allowed()`. This closes Finding 1 (26/36 previously-ungated handlers) in one place instead of per-handler, and per `TELEGRAM_ALLOWED_CHAT_IDS`/`telegram_access.allowed_chat_ids()` it resolves to the single Captain chat ID today. Commit `fc24c93` ("Close XO bot auth gap and token-in-logs leak"), already on `main`.
- **A proven "scoped service-account" pattern already exists on this exact platform**, built for a different (now-retired) bot: `core/infrastructure/supabase/migrations/0015_telegram_engineer_ro.sql` creates a `nolgin` Postgres role (`telegram_engineer_ro`), grants it to `authenticator` (so PostgREST can `SET ROLE` into it), and adds per-table RLS policies scoped to that role. `telegram-bot.DEPRECATED-2026-07-12/supabase_readonly.py` mints the JWT client-side (`jwt.encode({"role": "telegram_engineer_ro", "iat": ...}, SUPABASE_JWT_SECRET, algorithm="HS256")`, non-expiring by default — "acceptable for a long-running service whose secret can be rotated," per its own docstring) and sends it as the `Authorization: Bearer` header while keeping the anon key as the separate `apikey` gateway header. That bot was retired 2026-07-05 per the platform's "XO-only Telegram policy" (all other Telegram bots retired); its role and policies still exist in the DB but are unused. Its mandate was much narrower than XO's — 5 read-only tables + 1 append-only insert, vs. XO's 9 tables with 4 distinct write operations (`upsert` ×2, `insert` ×2, `update` ×3 call sites, `delete` ×1).
- **`SUPABASE_JWT_SECRET` is not currently provisioned** in either `telegram-bots/xo/.env` or `platform-runtime/.env` (grepped both; only reference on disk is `telegram-bot.DEPRECATED-2026-07-12/.env.example`). It would need to be pulled from the Supabase project settings before any custom-role JWT approach could be built.
- **`supabase-py` 2.3.4** (confirmed installed in `telegram-bots/xo/.venv`, the actual runtime) exposes `ClientOptions(headers=...)`, which in principle allows overriding the `Authorization` header independently of the `apikey`/`supabase_key` argument used to construct the client — the mechanism a custom-role approach would need. I did **not** verify end-to-end that this header override actually wins over the client's own default `Authorization: Bearer <supabase_key>` on every sub-client (postgrest, storage, realtime) it constructs — that would need to be confirmed before relying on it.

## 2. Does the bot need broad cross-table access for real functionality?

**No — its actual code path is narrow (9 tables, listed above) and does not need database-wide access.** But it does need genuine multi-table read/write across data owned by different domains (mission read, recovery/health writes, intelligence reads, capture queue read/write/delete) — there's no single Postgres role among the ones already provisioned (`anon`, `authenticated`, `service_role`) that matches that exact footprint. `authenticated` is both too broad (grants full access to 7 of the 9 tables to *any* authenticated caller, not just this bot) and too narrow (no DELETE policy on `captured_items`, so `handle_voice_debrief_decision_callback`'s delete would break unmodified). `service_role` is categorically too broad (all 112 tables, bypasses RLS entirely) but is the only currently-provisioned role under which every one of the bot's 10 write/read operations actually works today.

## 3. Options considered

### Option A — Keep `service_role`; treat the global auth gate as the real compensating control. **[Selected]**

**Reasoning:**
- RLS is a database-layer control: it distinguishes *which Postgres role* is running a query. It cannot see which Telegram chat, or which human, triggered that query from inside a single long-running bot process using one fixed credential — that information simply never reaches Postgres. No RLS policy shape, however written, could have closed Finding 1 (unauthenticated Telegram users reaching governance handlers). The fix for that had to be, and now is, an application-layer gate (`_global_auth_gate`) — this is not a workaround standing in for RLS, it's the only place in the stack where "which Telegram chat is this" is actually visible.
- For every table this bot touches, RLS *as currently configured* provides no additional narrowing over `service_role` anyway: 7 of 9 tables grant unrestricted `true`/`true` access to any `authenticated` principal, with zero per-user scoping. Swapping to a bare authenticated session would not meaningfully shrink this bot's blast radius on the tables it actually uses — it would mostly buy secure-by-default behavior on tables the bot *doesn't* touch, which is real but marginal value for a single-purpose, single-tenant, Captain-only bot (per the allowlist, this is not a multi-client surface RLS's per-user model is designed for).
- Tonight's own RLS-tightening pass (migration `0110`) independently reached the same conclusion for `recovery_pulses`: it deliberately kept a `service_role` INSERT policy specifically because the Telegram bot backend needs it and has no real authenticated session. This isn't a gap nobody has looked at — it's a call already made, consciously, by the same tightening effort that raised this finding.
- A naive move to a real `authenticated` session would be an active regression on at least one live path: `captured_items` has no `authenticated` DELETE policy, and `handle_voice_debrief_decision_callback` deletes a `captured_items` row on every "Start Debrief" action. That would need a new policy before any such switch, on top of everything else.
- Net: for this specific bot, `service_role` plus the (now-shipped) global chat-ID gate is the correct control for the actual threat model (an unauthorized Telegram user reaching a handler), and RLS was never going to be the layer that closed it.

**What this is not:** this is not "RLS doesn't matter, ignore it." Tonight's RLS tightening on `intelligence_events`/`intelligence_briefs`/`intelligence_source_registry`/`audit_events`/`comms_content_revisions` is still correct and valuable — it protects those tables from the anon/public-internet PostgREST surface (a real, different threat: a leaked anon key, a misconfigured frontend, a direct API caller). It's specifically *meaningless as an additional control for this one bot's own Supabase calls*, because those calls never go through the anon/authenticated surface RLS was tightened for — they go through a credential that bypasses RLS regardless of how tight the policies are. That's the whole finding, correctly stated, and Option A is the record that it's understood and accepted rather than silently true.

### Option B — Switch to a real `authenticated` Supabase Auth session (login-based). **Rejected.**

Feasibility: Supabase doesn't have a clean "persistent service-account session" primitive for `authenticated` — you'd need a real dummy user account, a login flow, and token refresh handling (`auto_refresh_token`/`persist_session` in `ClientOptions`) for a long-running process, which is real operational surface (refresh failures, expiry handling, credential rotation for a "user" that isn't a person) for no corresponding security gain here, per §1: the `authenticated` policies on this bot's tables are unscoped, and at least one path (`captured_items` delete) isn't even covered by an `authenticated` policy today. Not pursued further — dominated by Option C below, which gets the real benefit (scoped, fail-closed-by-default access) without the login/session machinery.

### Option C — Scoped custom Postgres role via a self-minted PostgREST JWT, reusing the platform's own `migration 0015` pattern. **Recommended next step — not implemented today.**

This is the option that would actually narrow blast radius: a new `nologin` role (e.g. `xo_bot`), granted to `authenticator`, with per-table/per-operation RLS policies matching exactly the 9 tables and ~10 operations enumerated in §1 (`select` on `missions`/`intelligence_briefs`/`intelligence_events`/`intelligence_source_health`/`intelligence_source_registry`; `select`+`upsert` on `recovery_pulses`; `insert` on `activity_logs`; `upsert` on `weight_logs`; `select`+`insert`+`update`+`delete` on `captured_items`) — reached via a JWT with a custom `role` claim, minted client-side from `SUPABASE_JWT_SECRET` (no login/session needed, matching the already-proven `mint_scoped_token()` pattern in the deprecated bot's `supabase_readonly.py`). This would take `service_role`'s reach from "all 112 tables, RLS bypassed" down to exactly this bot's real footprint, fail-closed on everything else by construction — genuine defense-in-depth against a future code change, a bug, or (given `cmd_message` runs a live LLM conversation loop) a prompt-injection-driven attempt to make the bot touch a table outside its intended set.

**Why not implemented now:**
1. `SUPABASE_JWT_SECRET` is not currently provisioned to this bot's environment — a new secret would need to be pulled from Supabase project settings and deployed, itself a change to a live credential surface.
2. It requires a new migration authoring per-table/per-operation policies precisely enough to not silently break a write path (the `captured_items` DELETE gap in §1 is exactly the kind of mistake this would need to avoid) — real authoring and review work, not a mechanical edit.
3. It requires changing how `app.py` constructs its Supabase client (`ClientOptions(headers=...)` override) — I confirmed the option exists in `supabase-py` 2.3.4 but did **not** verify the header actually takes precedence over the client's default `Authorization` header across every sub-client PostgREST/GoTrue/Storage build internally; that needs to be proven safe before depending on it in production.
4. Testing every one of the ~10 read/write paths (including the LLM/voice-capture flows) against a live, currently-serving-the-Captain bot is the right bar before shipping, and isn't something this investigation can fully discharge in one pass.
5. This is a live-production, security-relevant change to a governance-adjacent and health-data-logging bot — squarely a "major architecture change" under this persona's own escalation rule (SKILL.md: "Major architecture changes need Captain sign-off before proceeding"). Implementing it speculatively inside an investigation task, even a low-risk-looking piece of it, is exactly the kind of unilateral action that rule exists to prevent.

If the Captain wants to spend the engineering budget on this, the spec above (table list, operation list, the existing `0015` migration as a direct template, the `mint_scoped_token()` pattern to reuse, and the `captured_items` DELETE gap to fix along the way) is concrete enough to hand to an execution pass as its own scoped ticket.

## 4. `.env.example` note (already flagged in the original review, still true)

`telegram-bots/xo/.env.example:9` still documents `SUPABASE_KEY=<supabase-anon-or-service-role-key>` as if the two are interchangeable. Given this decision, the fix is to make that line state the actual, considered choice — e.g. `SUPABASE_KEY=<service-role key — required; this bot's Supabase calls bypass RLS by design, see xo-bot-service-role-decision.md>` — rather than leaving the current wording, which reads as an unconsidered toss-up. Not changed in this pass (doc-only, low-risk, but bundling it with a code commit for a decision doc felt like scope creep for this investigation) — worth a one-line follow-up.
