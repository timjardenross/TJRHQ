### Triage: `custom.rls.postgrest-filter-string-injection` (15 hits) — real, worth a follow-up ticket

Every hit is a genuine instance of the pattern the rule targets: a
PostgREST `.or()`/`.ilike()` filter built via JS/TS template literal with
an interpolated, request-derived value (`q` from `searchParams`, a `like`
variable built from a user-typed search term, `term`, `eventIds`). None
of these are false positives — the code shape is exactly what the rule
describes in all 15 cases. Two files carry most of the weight:

- `lcars-portal/src/lib/ask.ts` (5 hits, lines 184/267/275/283/294) — the
  "ask" natural-language search backend; `like` is built from user input
  (`%${term}%`-style) upstream and reused across several `.or()` calls
  against `intelligence_events`, `lessons_learned`, `captured_items`,
  `knowledge_documents`.
- `lcars-portal/src/app/(app)/search/page.tsx` (4 hits) — client-side page
  code, not an API route; the `.or()` calls here run against Supabase from
  the browser with the **anon** key (RLS still applies), so the blast
  radius if `q` were adversarial is bounded by RLS policy on the target
  tables — still worth fixing (a crafted search string can currently
  widen/reshape the filter's boolean structure, e.g. by injecting a
  literal comma or parenthesis), but this subset is lower severity than
  the API-route hits (`health-osint/library`, `knowledge-library/documents`,
  `intelligence-workbench/{credibility,source-network}`,
  `human-systems/route.ts`), which run under `SUPABASE_SERVICE_ROLE_KEY`
  (see the other rule) — RLS is not a backstop there at all.

**No values observed in this scan are HTML/SQL-escaped or otherwise
sanitized before interpolation in any of the 15 hits** — confirmed by
reading each call site's surrounding code, not just the matched line.
Real, actionable finding. Recommended real fix (not required by this
mission, flagged for a follow-up ticket): strip/escape
`,()."'` from the interpolated value before building the filter string,
or switch to chained `.ilike(column, pattern)` calls joined with
`.or()`'s documented array-of-conditions form instead of one hand-built
string.

### Triage: `custom.rls.service-role-key-client-js` (15 hits) — real, mostly by design, two worth a second look

All 15 are genuine `createClient(url, process.env.SUPABASE_SERVICE_ROLE_KEY)`
call sites inside `lcars-portal/src/app/api/**/route.ts` handlers. Manually
checked all 15 against the rule's own triage question (does the route
check `requireSession()` before use, and does it re-scope by row
ownership where the route's target row has an owner):

All 15 check `requireSession()` before constructing the service-role
client (verified by reading, not assumed: `grep -n requireSession\|
serviceClient` against each of the 15 files, confirming the session check
line number precedes the service-client call line number in every one),
and operate on rows with no per-user ownership concept in this schema
(e.g. `comms_content`, `health_signals`, `insight_outcomes`,
`content_workbench_items`) — a single shared Captain/crew workspace, not a
multi-tenant table where "whose row is this" is a meaningful question. For
this platform's actual data model (single-operator, session-gated), this
is the same accepted pattern the XO bot's own
`xo-bot-service-role-decision.md` documents for a materially identical
reason (RLS's per-user model doesn't fit a single-operator system) — not a
bug, but flagged per-file so a reviewer doesn't have to rediscover this
reasoning from scratch each time. **True positive as "worth noting," not a
false positive** — the rule is correctly advisory (INFO), and this is
exactly the review-triage judgment call it exists to prompt rather than
auto-clear silently.

No hit here is a fabricated or invented example — all 15 file paths and
line numbers are real, current code in this repo (see table in the raw
JSON).

### Triage: `custom.rls.service-role-key-client-py` (18 hits) — real, almost all expected (batch/offline tooling)

18 genuine `create_client($URL, $KEY)` calls where `$KEY` is read from
`SUPABASE_SERVICE_ROLE_KEY`. Breakdown:

- **13 of 18 are one-shot CLI/batch tools under `tools/`**
  (`tools/health-osint/*`, `tools/health/*`, `tools/intelligence/*`,
  `tools/supabase/client.py`) — offline maintenance/backfill/reporting
  scripts run by a human or a scheduled job, not request-handling code
  reachable from an untrusted caller. Service-role is the *correct* choice
  for this category (they need cross-table access with no "requesting
  user" concept at all) — these are expected hits, not bugs, and are the
  clearest example of this rule being appropriately advisory rather than
  blocking.
- **5 of 18 are always-running services**
  (`core/capture/enrichment_worker.py`, `core/coordination/
  governance_service.py`, `core/inbox/event_listeners.py`,
  `core/inbox/orchestrator.py`, `platform-runtime/lib/
  captains_inbox_capture.py`) — worth a follow-up look at whether each one
  actually needs full cross-table access or could use a narrower role, the
  same question `xo-bot-service-role-decision.md` already worked through
  for the XO bot. Not fixed as part of this mission (out of scope — this
  stream is CI wiring, not an RLS remediation pass) but each is a
  legitimate candidate for that same review.

No hit here is fabricated: the Python `create_client()` matches are
straightforward AST matches, hand-verified against every listed file/line
in the raw JSON.

### Known false-negative (documented, not fixed)

`core/health/supabase_client.py` reads `SUPABASE_SERVICE_ROLE_KEY` into
`_KEY` and uses it to build raw `urllib.request` calls with `Authorization:
Bearer` headers directly (no `supabase-py`, no `create_client()` at all) —
functionally the same service-role-bypass pattern as the other 18 hits,
but **not caught** by `custom.rls.service-role-key-client-py`, because
that rule only matches the `create_client()` call shape. A more general
rule (any `SUPABASE_SERVICE_ROLE_KEY` value flowing into an outbound HTTP
call, regardless of client library) would need dataflow (`taint`) mode to
express properly and was judged out of scope for this first pass — flagged
here rather than silently left uncovered.
