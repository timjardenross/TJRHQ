### Incident found and fixed: the timer was down (my earlier side-effect)

`systemctl list-timers | grep self-improving` returned nothing after the install. `self-improving-system.timer` was **inactive (dead) since 07:56:21 today, with no next trigger**. Cause: the timer has `Requires=self-improving-system.service`, so when I ran `systemctl stop self-improving-system.service` at 07:56 (to clear the 5-minute auto-restart wait during the llmsec recovery), systemd stopped the timer too and nothing restarted it. Tomorrow's 07:00 run would have been skipped. The earlier restore report did not catch this.

Fix: `systemctl start --job-mode=ignore-dependencies self-improving-system.timer` (so the `Requires=` did not start the service). Now: timer `active`, service `inactive`, next run **Fri 2026-11-06 07:04:25** (VERIFIED). This was the only action outside the brief; it restores the state I had disturbed. Lesson: stopping a unit that its timer `Requires=` also stops the timer; use `reset-failed`/`restart` or stop with `--job-mode=ignore-dependencies`. Worth checking the other timer/service pairs for the same `Requires=` shape (not done).

- Tables/columns that assume a dimension (from migrations, not queried live):
