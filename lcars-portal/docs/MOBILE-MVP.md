# MSN-IOS-001 — Starship Endeavour Mobile Command App MVP

Mobile-first Command Centre MVP for Captain TJR's iPhone. Reuses the existing
LCARS portal, Supabase data layer, XO workflows, Engineering lifecycle and
notification patterns. **No parallel backend. No broad portal redesign.**

The five MVP surfaces:

| # | Surface | Route | Reuses |
|---|---------|-------|--------|
| 1 | Captain's Chair | `/captains-chair` | `useCommandCentre`, `useROSData`, alerts engine |
| 2 | Quick Capture | `/capture` | `captured_items` (Captain's Inbox registry) |
| 3 | XO Chat | `/xo` + `/api/xo` | `buildShipContext`, XO role, Ollama upstream |
| 4 | Engineering Queue | `/engineering-queue` | `build_request_inbox`, `mission_delivery` |
| 5 | Push Alerts | `/alerts` | alerts engine over existing Supabase data |

---

## WP1 — Mobile App Strategy (recommendation)

**Decision: Progressive Web App (PWA) first. Native wrapper only later, only if justified.**

Rationale:

- The Command Centre is already a Next.js 14 + React + Tailwind app behind
  Supabase auth. Shipping a PWA reuses 100% of that stack — pages, components,
  data fetchers, RLS, middleware auth — with **zero** new backend.
- iOS 16.4+ supports installable PWAs ("Add to Home Screen") with standalone
  display, home-screen icon, and Web Push for installed apps. That covers the
  Captain's actual need (open from iPhone, act fast) without an App Store build.
- A native wrapper (Capacitor / native shell) is **deferred**. It is only
  justified if/when we need: background location, deep OS integration, App Store
  distribution, or reliable background push beyond what installed-PWA Web Push
  delivers. None of those are MVP requirements.

What was implemented for PWA / iOS readiness:

- `public/manifest.webmanifest` — name, standalone display, portrait, theme
  colour, maskable + any-purpose icons, and app shortcuts to the four action
  surfaces.
- `public/sw.js` — a deliberately conservative service worker: caches only the
  immutable icons/manifest (never navigations or auth responses), backs Web
  Notifications, and handles `notificationclick` deep-links. Registered via
  `components/ServiceWorkerRegister.tsx`.
- LCARS-themed PNG icons (`public/icon-192.png`, `icon-512.png`,
  `icon-maskable-512.png`, `apple-touch-icon.png`) generated by
  `scripts/gen-icons.mjs` (zero-dependency generator, re-runnable).
- `src/app/layout.tsx` — `manifest`, `appleWebApp`, `icons` metadata + a
  `viewport` export (`themeColor`, `viewport-fit=cover` for the notch/safe area).
- `src/middleware.ts` — allows `sw.js` + `manifest.webmanifest` through
  unauthenticated so the installable PWA can load them.

**Authentication / security:** unchanged. The existing Supabase SSR middleware
still gates every route; the new surfaces sit behind it. The service worker
intentionally does **not** cache authenticated pages or API responses, so there
is no risk of serving a stale signed-in/out view. RLS continues to govern all
reads/writes — Quick Capture writes only to tables the `authenticated` role is
explicitly permitted to write.

**Reuse-first architecture:** every new surface is a thin UI + a small typed
fetcher over data the portal/Slack/Telegram systems already populate. New
library files (`capture.ts`, `engineering-queue.ts`, `alerts.ts`) contain only
read/normalise/route logic — no new storage.

## WP2 — Captain's Chair: Daily Operating Picture

`components/MobileOperatingPicture.tsx` renders an iPhone-first card stack at the
top of `/captains-chair` (mobile only, `lg:hidden` — the desktop grid is
untouched). It composes existing hooks into:

- **"What needs my decision?" banner** — counts decision/escalation alerts, names
  the top one, links to `/alerts`. Green "Nothing right now" when clear.
- **Today's capacity** — recovery posture band + message (`useROSData`).
- **Top priority** — the recommended action from the unified daily operating
  picture (`useCommandCentre` → `human_systems_recommendations`).
- **Escalations** — escalation + critical-wellness alerts.
- **Mission state / readiness** — ship-status domains (`useCommandCentre` →
  human systems, delivery, resilience, knowledge, infrastructure).
- **Blocked / failed** — links to the Engineering Queue when work is blocked.

## WP3 — Quick Capture

`/capture` — single input box first; an optional, collapsed type selector
(Note / Mission / Health log / Idea). `lib/capture.ts` routes every capture into
the **existing** Captain's Inbox capture registry (`captured_items`,
MSN-DISCOVERY-001) — no duplicate capture backend. The type maps onto the
registry's existing `classification` field so downstream governance/triage
routes it:

| Type | `classification` | Downstream |
|------|------------------|-----------|
| Note | `reference` | kept for context |
| Idea | `research` | research / roadmap triage |
| Mission | `mission` | promoted to build/mission pipeline; surfaced in Engineering Queue & alerts |
| Health log | `personal` | surfaced to Medical, **non-destructive** |

Health note: a *structured* check-in still uses the existing `/medical/check-in`
page (which upserts `health_daily_logs`). Quick Capture only records a
lightweight health note, so it never clobbers the day's structured upsert; the
screen offers a one-tap link to the full check-in.

`captured_items` enforces NOT NULL `source_*` columns and a constrained
`source_type`; capture synthesises a stable `lcars-mobile-quick-capture`
envelope with a UUID `source_message_id` (uniquely indexed → idempotent inserts).

## WP4 — XO Chat

`/xo` + `/api/xo`. Reuses the **same** Ollama Cloud upstream and env flags as the
AI Console, the existing XO role prompt (`ai-roles.ts`), and — critically — the
existing `buildShipContext()` (`ai-context.ts`) so XO already knows missions,
decisions, today's health, knowledge and command memory **without the Captain
pasting anything**. It does not simply resurface data:

- A "MOBILE XO MODE" doctrine steers brief, answer-first replies and requires
  every reply to end with a single `→ Next action:` line, which the UI surfaces
  as a highlighted next step.
- An always-present action row turns intent into action **even when the model is
  offline**: *Capture as mission*, *Capture as note* (both via `captured_items`),
  *Open Engineering Queue*, *Open Alerts*.
- Approvals/governance: XO is advisory (per its role prompt) and flags decisions
  for the Captain; the actual approve/reject happens in the Engineering Queue
  where the existing build-inbox lifecycle allows it.

## WP5 — Engineering Queue

`/engineering-queue`. Reuses `build_request_inbox` (governance triage queue,
migration 0015) and the `mission_delivery` view (EDO instrumentation, migration
0023, via `delivery.ts`). `lib/engineering-queue.ts` normalises every real
status / delivery-state into the mandated lifecycle:

`Pending Triage → Assigned → In Progress → Awaiting Review → Completed`

Surfaces: **next engineering action** (blocked → awaiting-review → triage),
**blockers** (reuses the delivery bottleneck detector), lifecycle count filters,
per-item next-action, and **Approve / Reject** on build-inbox items that are
awaiting review. Approve/reject writes `build_request_inbox.status` and reports
the real outcome (including an RLS message if the role lacks write access) — it
never silently no-ops.

## WP6 — Push Alerts

`lib/alerts.ts` derives alerts entirely from existing Supabase data (no new alert
tables). Only five classes are permitted, each strictly gated; **no FYI/nominal
alerts are ever emitted**. Every alert carries a `why` ("Why does Captain TJR
need this now?").

### Alert rules

| Class | Fires when | Severity | Source (existing) |
|-------|-----------|----------|-------------------|
| `escalation` (red flag) | Health red-flag text detected in today's log | critical | `loadHumanSystems` → `scanEscalation` |
| `wellness` | Recovery posture = REST, or capacity band = depleted | critical | `fetchRecoveryPosture`, `loadHumanSystems` |
| `escalation` | Recovery debt = high (low-capacity run + short sleep) | high | `loadHumanSystems` → `recoveryDebt` |
| `wellness` | Emotional-load flag raised (≥3/7 days activated/dysregulated) | high | `fetchEmotionalLoadFlag` |
| `delivery_failure` | Mission delivery state = `blocked` (per item, capped 4) | critical | `loadDelivery` |
| `delivery_failure` | ≥1 failed dispatch in last 3 days | critical | `mission_execution_events` |
| `eng_review` | P0/P1 mission `in_review` (capped 4) | high | `loadDelivery` |
| `eng_review` | Build request `in_review`/`awaiting_review` | high | `build_request_inbox` |
| `decision` | Captured `mission` items still `unreviewed` | high | `captured_items` |

Healthy conditions produce **no** alert. Alerts are de-duped and sorted by
severity.

### Delivery / notifications

- **In-app:** the Alerts centre (`/alerts`) and a live count badge on the mobile
  command bar.
- **Local Web Notifications:** `useAlerts` (owned by the always-mounted command
  bar) fires a banner **only** for newly-appeared critical/high alerts, never the
  same alert twice (signature persisted in `localStorage`). On installed iOS
  PWAs these render as system banners. Opt-in via the Alerts screen.
- **Future — true server push (closed app):** requires VAPID keys, a
  `push_subscriptions` table, and a Supabase **edge function** to send Web Push.
  Deferred to the native/edge phase (see below) to avoid standing up sending
  infrastructure for MVP.

## WP7 — Mobile UX / LCARS fit-for-iPhone

- `components/MobileCommandBar.tsx` — fixed, thumb-friendly bottom tab bar for the
  five surfaces, with a live alert badge. **Mobile-only (`lg:hidden`)** so the
  desktop portal is unchanged. Safe-area padding for the iPhone home indicator.
- Cards are single-column, large-tap-target, readable type; clutter is reduced on
  mobile by scoping the heavy desktop Captain's Chair grid below the mobile
  operating picture.
- LCARS palette/components reused throughout (`LCARSPanel`, `StatusBadge`,
  `departments.ts` tones) — LCARS feel without sacrificing usability.
- Only the five MVP surfaces were touched; no other page was redesigned.

## What remains for a future native iOS phase

1. **True background Web Push** — VAPID keypair, `push_subscriptions` table, a
   Supabase edge function to evaluate the alert rules server-side and send Web
   Push so alerts arrive with the app fully closed. (MVP fires local
   notifications while the installed PWA is alive/backgrounded.)
2. **Native wrapper (Capacitor)** — only if App Store distribution, richer OS
   integration, or guaranteed background delivery is required.
3. **Engineering approve/reject RLS** — add an explicit `authenticated`
   write policy (or a service-role RPC) for `build_request_inbox` so Captain
   approvals persist regardless of the project's current RLS posture.
4. **Offline capture queue** — buffer Quick Captures locally and replay on
   reconnect.
5. **Biometric unlock / app-lock** for the installed PWA.
6. **Richer XO actions** — let XO directly create `build_request_inbox` rows and
   propose decisions once a write path/RPC exists.
