# USS-TJR-MSN-0001 — Number One Assignment Authority

Status: DRAFT
Owner: Captain TJR
Supporting Specialists: XO, Number One, Engineering
Priority: P1 High
Created: 2026-06-12

## Objective

Discover, define, and prepare the implementation of Number One as the canonical Assignment Authority responsible for transitioning approved engineering work from `APPROVED_FOR_ENGINEERING + PENDING` to `APPROVED_FOR_ENGINEERING + SUBMITTED`, without introducing governance bypasses, duplicate execution paths, unclear ownership, or audit gaps.

## Context

The governance model is now ratified:

- XO is governance approval only and cannot create `SUBMITTED`.
- Engineering agents are execution-only and cannot create `SUBMITTED`.
- `/batch-claim` currently behaves as the provisional Assignment Authority and must be retained as a compatibility interface during migration.
- `SUBMITTED` means eligible for execution and available to be claimed.
- `CLAIMED` means reserved by a specific execution worker.
- Assignment authority is separate from governance approval authority and execution authority.

This mission prepares the implementation boundary for Number One without authorizing code changes yet.

## Scope

### In Scope
- Formalize the assignment authority model for Number One.
- Define the semantic boundary between `SUBMITTED` and `CLAIMED`.
- Define canonical active assignment record behavior.
- Define duplicate and concurrent request handling.
- Define recovery behavior for conflicting assignment attempts.
- Define migration and compatibility handling for `/batch-claim`.
- Produce the implementation-ready policy and control surface for later coding work.

### Out of Scope
- Code changes.
- Database migrations.
- Workflow mutations.
- Agent execution-path changes.
- New direct execution surfaces.
- Replacing existing `/batch-claim` behavior during this mission.

## Deliverables

1. Assignment Authority implementation plan.
2. Canonical state and transition model for `PENDING -> SUBMITTED -> CLAIMED -> IN_PROGRESS -> COMPLETED -> CLOSED`.
3. Duplicate and concurrency control specification.
4. Audit and evidence requirements for assignment decisions.
5. Migration strategy for keeping `/batch-claim` as a compatibility interface.
6. Implementation roadmap with minimal blast radius.

## Acceptance Criteria

- Number One is explicitly defined as the canonical owner of `SUBMITTED`.
- `SUBMITTED` and `CLAIMED` have separate, unambiguous semantic meanings.
- One canonical active assignment record per work item and assignment intent is defined.
- Duplicate and concurrent assignment requests are specified to return the existing canonical record or a safe already-assigned response.
- Recovery behavior is specified to reconcile to a single canonical assignment record.
- `/batch-claim` compatibility handling is documented.
- No implementation work is performed.

## Validation Expectations

- Review the mission against ADR-0003 and the ratification note.
- Produce a design artifact that can be used as the implementation source of truth.
- Confirm the design preserves separation of duties and fail-secure behavior.

## Next Step

Use the approved mission design to author the implementation plan and, only after approval, begin coding the Assignment Authority layer.
