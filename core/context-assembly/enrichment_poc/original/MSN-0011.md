# USS-TJR-MSN-0011 — Slack Supabase Commander Integration

Status: IN_PROGRESS
Owner: Chief Engineer
Supporting Specialists: Chief of Staff, Knowledge Officer
Priority: P1 High
Created: 2026-06-06

## Objective

Connect the Slack Commander interface to Supabase persistence so explicit Commander events can be captured without changing the repository as the source of truth.

## Architecture

Slack remains the live interface. Supabase records operational memory and decision intelligence. Markdown in GitHub remains the durable human-readable knowledge base.

Flow:

Slack message -> `slack-bot/commander_bridge.py` -> existing Commander router/runtime -> optional Supabase persistence.

## Scope

- Capture Commander events from Slack mentions.
- Classify explicit decision, mission candidate and memory/context intents.
- Persist structured records to Supabase when credentials are configured.
- Preserve existing Slack behavior for general Commander questions.
- Run safely when Supabase is disabled or temporarily unavailable.

## Deliverables

- Supabase client wrapper in `tools/supabase/client.py`.
- Slack bridge in `slack-bot/commander_bridge.py`.
- Supabase schema contract in `tools/supabase/schema/MSN-0011-Supabase-Commander-Schema.sql`.
- Tests for disabled mode, intent payloads, routing and fallback behavior.

## Acceptance Tests

- `Decision: Defer BFG cleanup until token rotation is confirmed.` creates a decision draft.
- `Create mission: Build Slack to Supabase Commander integration.` creates a mission candidate.
- `Remember: Supabase is persistence, not the source of truth.` creates a memory event.
- `Who should own the governance source of truth?` still routes through the Commander runtime.

## Known Limitations

- Supabase writes are insert-only for this mission.
- The schema is provided as a contract SQL file rather than a production migration.
- Runtime authentication and RLS are intentionally out of scope.
